# AgriVision — Advanced AI Upgrade: MoE Experts, Fine-Tuning, Context-Aware Advisory, LLM Fine-Tuning, RAG Improvement

## 1. Objective
Upgrade AgriVision's Zone 1 specialist architecture into a technically defensible, learned-gated Mixture-of-Experts (MoE) system with fine-tuned crop/livestock experts; add region/season/weather-aware contextual advisory generation across local and cloud paths; fine-tune an open LLM (LoRA/QLoRA) as a Gemini alternative for grounded advisory generation; and materially improve RAG quality, citation correctness, and evaluation. This is a multi-phase, dataset- and compute-heavy roadmap — every phase requires explicit user approval before implementation, and every claim of accuracy/performance must come from an actual measured run the user executes, never a fabricated number.

## 2. Current Repository Baseline
Source of truth: `current_repo_status.md`, `code_files.md` (the coding agent must re-verify all of this against the live repository in each phase's audit step — these are summaries, not guarantees of current state):
- Zone 1: `pipeline.py` orchestrates quality-check → `task_router.py` (HF zero-shot crop-vs-livestock classification) → `crop_expert.py`/`livestock_expert.py` (each wraps `BaseImageExpert`, loads an HF vision checkpoint, with mock-label fallback under unspecified conditions) → `fusion.py` (rule-based bonus/penalty arithmetic) → `confidence_gate.py` (static thresholds, 0.80 safety-critical) → local advisory (via `knowledge/`) or cloud escalation.
- Zone 2: `gemini_client.py` (+ `MockGeminiClient`) sends structured evidence to Gemini; `validator.py` checks response schema; `retriever.py` uses FAISS + `sentence-transformers/all-MiniLM-L6-v2` over a local `knowledge_base/` of markdown documents.
- Zone 3: SQLite (`farm_memory.py`) stores observations/diagnoses/advisories; `get_farm_history()` produces text history strings for Zone 2.
- Contracts (`contract.md`, protected/frozen): (1) image-prediction `{"domain","input_type","prediction","confidence","top_k"}`, (2) ASR text `{"text","language","confidence"}`, (3) text evidence `{"symptoms","crop","severity_hint"}`, (4) sensor data `{"domain","temperature","activity","feed_intake","anomaly"}`, (5) fusion output `{"prediction","visual_confidence","text_support","sensor_support","evidence_agreement","final_confidence","route"}`, (6) cloud payload `{"domain","image_prediction","visual_confidence","farmer_text","text_evidence","sensor_data","farm_history","retrieved_knowledge"}`.
- Existing terminology gap: "MoE" is currently only a router + two independent experts, not a genuine gated/learned MoE — this roadmap's Phase 0 exists specifically to close that gap honestly.
- No region/season/weather field exists anywhere in the current contracts or pipeline — this is new context data that must be added to the schema (see Section 11).
- No prior fine-tuning, no prior LLM fine-tuning, no prior RAG evaluation exists in the repository per the supplied audit.

## 3. Scope
**In scope (across phases):** genuine gated-MoE-style crop/livestock expert architecture; fine-tuning of crop and livestock vision experts with a gradual-unfreezing/differential-LR strategy and full measurable evaluation; region/season contextual data flow into local advisory and cloud payload; weather-API integration for the cloud path; LoRA/QLoRA fine-tuning of an open LLM as a citation-grounded advisory generator, benchmarked against Gemini; RAG knowledge-base expansion, chunking/embedding/retrieval quality improvement, citation-correctness tracking and evaluation, and a justified (not default) decision on cloud-hosted vector DB migration.
**Out of scope for this task.md's phases (all deferred to later, separate approval cycles):** farm memory image storage, admin dashboard, secure aggregation/federated learning, real IoT sensor hardware, voice/ASR quality improvements (ASR remains as currently implemented/disabled per prior roadmap phases — not touched here), any multi-agent Zone 2 redesign beyond what Task 4/5 explicitly requires, production-scale infra beyond what's needed to demo this roadmap.

## 4. Overall Target Architecture / Change Direction
Zone 1 evolves from `router → {crop_expert, livestock_expert}` into `domain router (crop/livestock, kept largely as-is) → domain-specific gated MoE (2 fine-tuned sub-experts per domain, lightweight learned or scored gate, top-1 or confidence-weighted top-k combination) → fusion → confidence/safety gate (unchanged mechanism, now also consuming region/season context) → local advisory (now region/season-aware) or cloud escalation`. Zone 2 evolves from `Gemini + RAG` into `context-assembled (region+season+weather+evidence+RAG+farm history) → either Gemini OR a fine-tuned local/self-hosted LLM (LoRA/QLoRA) → structured, cited advisory`, with the choice between Gemini and the fine-tuned LLM being a configurable, evaluated decision, not an assumed replacement. Zone 3 gains no structural change beyond exposing farm history data needed for LLM fine-tuning data generation and citation tracking. The existing local-vs-cloud confidence gate remains entirely distinct from the new intra-domain MoE gate — they operate at different pipeline stages and must never be conflated in code, naming, or documentation.

## 6. Detailed Requirements Per Phase

### Phase 0 — MoE Architecture Design & Router Mechanism (Task 1)
**Design analysis required before any file changes:**
- **Four-expert count:** Justified only if the PlantVillage split and livestock split below hold up under Phase 1's actual class-wise baseline evaluation. The coding agent must not assume 4 experts are correct — it must verify, in Phase 0's audit, that the current crop/livestock experts' underlying checkpoints and label sets are compatible with being split into sub-groups at all (e.g., confirm whether a single fine-tuned backbone can realistically be forked into two class-subset heads, or whether two entirely separate fine-tuning runs are needed).
- **PlantVillage grouping:** The proposed split (Corn/Bell pepper/Potato/Soybean/Tomato ≈ 20 classes vs. remaining fruit-tree classes ≈ 18 classes) is a **row-crop vs. tree/perennial-crop** split, not a "fruit vs. vegetable" split as originally phrased (e.g., tomato and bell pepper are botanically fruits but are annual row crops) — the coding agent must verify the exact 38-class list and finalize the two groups by crop-growth-pattern similarity (annual row crops vs. perennial tree/vine crops), since visually and agronomically related classes benefit more from being co-located in one expert than an arbitrary fruit/vegetable label would. Document the finalized 20/18 (or corrected) split with the exact class list in the Phase 0 plan.
- **Livestock split:** Two-expert split (LSD-vs-healthy, FMD-vs-healthy) is reasonable **if and only if** Phase 0's audit confirms sufficient per-class image counts exist for both diseases plus a shared/separate healthy class in the available Cattle Diseases Dataset — if the FMD class is too small to fine-tune reliably, the coding agent must flag this explicitly rather than proceeding with an under-supported expert, and propose folding FMD detection into a documented future-scope note instead of shipping an unreliable third-class output.
- **Router mechanism (domain-first, hierarchical):** Keep the existing crop-vs-livestock zero-shot domain router unchanged in mechanism (per prior roadmap phase decisions — do not retrain it). Add a **second-level intra-domain gate** that selects which of the 2 sub-experts within the already-determined domain should run. This second-level gate must be clearly and permanently distinguished in naming/code/docs from the Zone 1 local-vs-cloud confidence/safety gate — e.g., name it `expert_gate` or `moe_gate`, never `confidence_gate` — to avoid the exact conflation risk called out in the requirements.
- **Gate training approach:** Since experts are two independently fine-tuned pretrained models (not a jointly trained MoE with a shared backbone), a full learned neural gate would need its own labeled routing dataset. The technically justified, still-genuinely-MoE-defensible approach: derive the intra-domain gate from a **lightweight trained classifier** (e.g., a small linear/logistic classifier or a shallow MLP on top of a frozen shared feature extractor — reuse the same zero-shot backbone or a small embedding model already in the pipeline) trained on the same class-grouping labels used to fine-tune the two sub-experts, since that labeled data already exists once Phase 1's datasets are assembled. This makes the gate genuinely learned (not zero-shot, not hardcoded rules), satisfying the "confidently claim MoE" requirement, while remaining lightweight and edge-feasible. The coding agent must confirm this is feasible with the confirmed class groups from Phase 1's dataset audit before finalizing.
- **Top-1 vs top-k combination:** Recommend **top-1 hard routing** (the gate selects exactly one sub-expert to run, not both) for edge feasibility — running both sub-experts per domain doubles on-device inference cost for a farmer's phone with no clear accuracy benefit at only 2 experts per domain. Only fall back to top-k soft combination if Phase 0's audit finds a specific, documented reason top-1 routing produces poor accuracy on the confirmed class groups (e.g., high confusion between the two groups) — this must be evaluated with real data in Phase 1, not assumed at design time.
- **Compute reasonableness:** Total on-device model count becomes: 1 domain router (existing, unchanged) + 1 lightweight intra-domain gate (new, small) + up to 2 active sub-experts per domain (but only 1 invoked per case under top-1 routing) — i.e., at most 2 models run per inference (gate + 1 expert) beyond the existing domain router, which is a modest, edge-reasonable increase over the current 1-router + 1-expert-per-domain design.
**Constraints:** No shared-backbone joint MoE training (infeasible with only 2 pretrained checkpoints and hackathon-scale compute/data). No change to the domain-level (crop-vs-livestock) router mechanism itself. No conflation of the new intra-domain gate with the existing local-vs-cloud confidence gate anywhere in code or docs.
**Acceptance criteria:** A written, dataset-verified design document specifying: final PlantVillage class groups (with counts), final livestock class groups (with counts, and an explicit flag if FMD is under-supported), the intra-domain gate's exact mechanism and training data source, top-1 routing decision (or a documented, data-justified exception), and a clear naming/interface contract distinguishing `moe_gate` from `confidence_gate`. No model training occurs in this phase — design and data-audit only.

### Phase 1 — Expert Fine-Tuning & Evaluation (Task 2)
**Requirements:**
- **Dataset/model research (must be done against real, verifiable sources, not assumed):** Confirm PlantVillage's exact class list/counts and licensing; confirm the specific Cattle Diseases Dataset's exact class list/counts/source and licensing. Identify 1–2 candidate lightweight pretrained backbones per domain (e.g., MobileNetV2, EfficientNet-Lite/B0 class) suitable for CPU/edge inference and available via `timm`/HuggingFace with permissive license — do not assume a single "best" model without checking availability first.
- **Fine-tuning strategy (per the explicit requirement — no simple frozen-head-only or full-unfreeze-only):** Implement a **phased, gradual-unfreezing schedule**: Phase A — train only the classification head (backbone frozen); Phase B — unfreeze the top N backbone blocks/layers, continue training at a lower learning rate; Phase C — unfreeze the full backbone, fine-tune end-to-end at a further-reduced learning rate. Combine with **differential learning rates** across the three unfreezing stages (head LR > mid-layer LR > early-layer LR) rather than a single global LR at each stage. Exact N (number of layers unfrozen at Phase B) and exact LR values must be chosen empirically per backbone during implementation, not fixed in this task.md — validated via validation-set performance at each stage, with checkpoint selection based on best validation macro-F1 (not just accuracy, given expected class imbalance).
- **Train/val/test strategy:** Stratified split (e.g., 70/15/15 or dataset-convention split if PlantVillage/Cattle dataset has an established split) per class group, with class-imbalance handling (class-weighted loss or oversampling) considered where the confirmed class counts are skewed.
- **Baseline-first:** Before any fine-tuning, run the evaluation tooling from the prior roadmap's Phase 1 baseline work (if present in the repo — the coding agent must locate it in the audit step; if absent, create the minimal equivalent) against the **current unmodified experts** to establish a true "before" number. Do not skip this — the entire measurable-improvement story depends on it.
- **Metrics:** accuracy, per-class precision/recall, macro-F1, confusion matrix, and calibration (reliability by confidence bucket) for each of the 4 sub-experts individually, plus end-to-end domain-level (crop overall, livestock overall) metrics combining gate + sub-expert. No target/expected accuracy values are to be stated anywhere in code/docs produced by this phase — only measured, reported values from runs the user actually executes.
- **The coding agent does not execute training or evaluation itself** (GPU/compute-heavy, and per Section 18 safety rules) — it prepares training scripts, data-loading/preprocessing code, the fine-tuning loop implementing the phased-unfreezing/differential-LR strategy, and the evaluation/reporting scripts, then hands the user exact commands to run each stage.
**Constraints:** No training from scratch. No architecture larger than what's edge/CPU-feasible for the target backbones identified. No fabricated results.
**Acceptance criteria:** Baseline evaluation script + results (run by user) exist for current experts; fine-tuning scripts implementing the 3-stage gradual-unfreezing + differential-LR strategy exist for all 4 sub-experts; evaluation scripts produce the full metrics list above per sub-expert and per domain; a written before/after comparison exists once the user runs both; the intra-domain `moe_gate` from Phase 0 is trained using the same finalized class-group labels and evaluated for routing accuracy separately from sub-expert classification accuracy.

### Phase 2 — Contextual Data Flow: Region/Season/Weather (Task 3)
**Requirements:**
- **Region/season:** Add region and season as new, explicit fields flowing from farmer input (or device/profile metadata — the coding agent must audit whether the existing UI/Zone 3 farm profile already has a region field before assuming a new UI input is needed) into: (a) local advisory lookup (season/region can modify which preventive-action text or timing guidance is shown for a matched disease class, without altering the underlying classification/advisory-mapping mechanism from the prior roadmap's Phase 2 work), and (b) the Zone 2 cloud payload.
- **Weather (cloud-only, since edge is offline-first):** Integrate a weather API call in the Zone 2 pipeline only (never Zone 1, to preserve offline-first guarantees) using farm region/location to fetch current conditions relevant to disease risk (temperature, humidity, recent rainfall). The exact provider must be selected by the coding agent during this phase's audit/plan step based on: free-tier availability, no-API-key-required or easily-configurable-key options, reliability, and India-coverage — proposed as one definitive recommendation in the Phase 2 plan for user approval, not left as an open menu.
- **Contract impact:** Region/season/weather are **additive** fields. The cloud payload contract's existing required fields (`domain, image_prediction, visual_confidence, farmer_text, text_evidence, sensor_data, farm_history, retrieved_knowledge`) must remain present and unchanged in meaning; new fields are added following Section 11's contract-change process (identify → justify → get explicit approval → then modify `contract.md`, since this is a case where a contract change is genuinely necessary and must not be done silently).
- **Where NOT to use context:** Region/season/weather must not feed into the crop/livestock visual classification models themselves (Phase 1's experts) or into the Phase 0 MoE gate — vision classification stays purely image-based; context modifies only advisory text/recommendations and cloud reasoning, not the disease prediction itself. RAG query construction (Phase 3) may optionally include season/region as retrieval filters if the knowledge base supports it — flag this as an option to decide in Phase 3, not implement here.
**Constraints:** No weather dependency introduced into the offline/local path. No API key handling that violates Section 18 safety rules (the coding agent configures where the key is read from `.env`, never reads/prints/logs the key's value itself).
**Acceptance criteria:** Region/season fields flow correctly into local advisory output and the (contract-approved) extended cloud payload; a weather API integration exists in Zone 2 only, using a documented, approved provider, with graceful degradation (advisory still generates correctly, minus weather context, if the API call fails or is unavailable) — tested via the user manually toggling network/API availability per the provided verification commands.

### Phase 3 — RAG Improvement & Evaluation (Task 5)
**Requirements:**
- **Knowledge-base coverage:** Expand the local knowledge_base's document count and coverage to match the final class list confirmed in Phase 1 (every crop/livestock condition the fine-tuned experts can actually predict should have at least one grounded knowledge document) — the coding agent must audit current KB coverage against Phase 1's final class list and identify gaps explicitly rather than assuming full coverage.
- **Document quality/metadata:** Add structured metadata (source, condition/class tag, region-applicability if relevant, last-updated) to each KB document to support both better retrieval filtering and citation display.
- **Chunking/embeddings:** Review current chunking strategy (if any) and the `sentence-transformers/all-MiniLM-L6-v2` embedding choice; only change either if the audit or a quick retrieval-quality check (Section 9) shows a concrete deficiency — do not swap embeddings/chunking speculatively.
- **Retrieval/reranking:** Evaluate whether a lightweight reranking step (e.g., cross-encoder rerank of top-k FAISS results) measurably improves relevance on a small manually-labeled query set before adding it — if the baseline top-k retrieval is already adequate, do not add reranking merely for sophistication.
- **Cloud vs. local vector DB decision:** The suggestion of "shift to some cloud-based database" must be evaluated, not defaulted to. The coding agent must produce a comparison (current local FAISS file vs. a cloud-hosted vector DB option) covering: does the actual query volume/document count in this hackathon-scale KB justify cloud infrastructure; does moving to cloud break the offline-first Zone 1 local-advisory guarantee (it should not, since RAG is already Zone 2/cloud-only); does it introduce new latency/cost/API-key-management burden. **Default recommendation unless the audit finds a specific technical blocker with local FAISS:** keep local FAISS, since it is already Zone 2-only (no offline-first conflict), free, and simple — cloud migration is justified only if document count grows to a scale where local FAISS becomes measurably slow or hard to maintain, which must be checked empirically, not assumed.
- **Citation correctness:** Implement/verify that every advisory-generation call (whether via Gemini now or the fine-tuned LLM later in Phase 4) receives retrieved documents tagged with stable, referenceable IDs, and that the output schema (via `validator.py`) requires the model to cite which specific document ID(s) informed each claim. Add a post-generation citation-verification check: does the cited document ID actually exist in the retrieved set for that call (catches hallucinated citations).
- **Farm-history citation:** Similarly verify/require that when farm history informed the advisory, the output explicitly references which historical observation(s) it used, and that this reference is checked against the actual farm-history payload sent, not fabricated.
- **Evaluation:** Build a small manually-curated query/relevance test set (e.g., 15–25 queries mapped to expected-relevant document IDs) to measure retrieval precision/recall@k, and a citation-correctness rate (fraction of generated advisories whose cited document IDs are valid and actually retrieved) — the coding agent prepares this tooling; the user runs it and supplies/reviews the manually-curated relevance judgments, since the coding agent cannot fabricate domain-expert relevance labels.
**Constraints:** No cloud vector DB migration without the documented, approved justification above. No claim of "improved RAG" without the before/after retrieval-quality numbers from the user's actual run.
**Acceptance criteria:** KB coverage gap analysis complete and gaps filled for all Phase-1-confirmed classes; document metadata schema implemented; a documented, justified decision on local-vs-cloud vector DB (default: keep local, unless audit finds otherwise); citation-ID tagging and a hallucinated-citation-detection check implemented; farm-history citation-correctness check implemented; retrieval evaluation tooling exists and produces precision/recall@k and citation-correctness-rate reports once the user runs it with their curated relevance set.

### Phase 4 — LLM Fine-Tuning (LoRA/QLoRA) & Cloud Integration (Task 4)
**Requirements:**
- **Base model candidates:** The coding agent must research and propose 1–2 concrete open-weight candidates appropriate for LoRA/QLoRA fine-tuning at a size compatible with realistically available training compute (e.g., a 1–4B or up to ~7-8B parameter instruction-tuned model from the Qwen2.5/Llama-3.x class, confirmed against actual current availability and license terms at implementation time — do not assume a specific version number without checking, since model availability changes over time) — presented as one definitive recommendation with a brief justification (size/hardware fit, license, chat-template documentation quality), not an open-ended menu.
- **Training data — do not assume SQLite history is sufficient:** Per the explicit requirement, existing local advisory/observation records in SQLite are very likely too few, too structurally rigid (they are lookup-table entries from the prior roadmap's Phase 2 local-advisory work, not natural-language advisory narratives), and not diverse enough to fine-tune a generative LLM directly. The coding agent must: (a) audit exactly how many real (non-mock) historical records exist and their structure, (b) if insufficient (likely), design a synthetic-data-generation strategy — e.g., using Gemini itself (already integrated) to generate a diverse set of realistic advisory examples conditioned on the same structured inputs (prediction + evidence + RAG snippets + region/season/weather) the fine-tuned model will eventually receive, explicitly logging that these are synthetic and require human spot-check review before use as training data, (c) define a clear human-validation/quality-control step the user performs on a sample of the generated data before full-scale generation, since the coding agent cannot itself validate agronomic/veterinary correctness.
- **Input/output format:** Define a fixed structured input template (prediction, confidence, evidence, region/season/weather, RAG snippets with IDs, farm history with IDs) and a fixed structured output format requiring the same citation-ID and farm-history-reference fields required of Gemini in Phase 3, so the fine-tuned model is a drop-in alternative to Gemini in the existing pipeline slot, validated against the same `validator.py` schema (extended, not replaced).
- **Chat template compatibility:** Explicitly verify and use the exact chat template published for the chosen base model (via its tokenizer config / model card) — mismatched templates are a common, silent source of degraded fine-tuned model quality; the coding agent must not assume a generic template.
- **LoRA/QLoRA strategy:** QLoRA (4-bit quantized base + LoRA adapters) is the default recommendation for compute efficiency given likely hackathon-tier GPU access (e.g., a single consumer/Colab-tier GPU); LoRA-only fine-tuning is used only if the audit finds sufficient GPU memory to skip quantization — this decision must be made explicitly in the Phase 4 plan, not left open.
- **Train/val/test split:** Stratified across advisory categories/conditions, holding out a test set never used in training or validation for final comparison against Gemini.
- **Comparison with Gemini:** Evaluation must compare the fine-tuned LLM against Gemini on the same held-out test inputs for: citation-correctness rate (from Phase 3's tooling), farm-history-reference correctness, structured-output-schema validity rate, and (only if the user can provide or facilitate human/expert review) qualitative advisory-quality judgment — the coding agent does not fabricate a "better than Gemini" or "worse than Gemini" conclusion; it reports whatever the user's actual run produces.
- **Inference integration:** The fine-tuned model becomes a second, configurable backend in Zone 2 alongside Gemini and `MockGeminiClient` (e.g., a `LocalLLMClient` implementing the same interface), selectable via config — not a replacement that removes the Gemini path, so the system retains a fallback and a basis for ongoing comparison.
**Constraints:** No execution of GPU training/fine-tuning by the coding agent itself. No calls to the Gemini API by the coding agent for synthetic data generation — the coding agent prepares the generation script/prompts; the user runs the actual generation calls (per Section 18, Rule 10 — never execute commands that call the Gemini API). No fabricated comparison results.
**Acceptance criteria:** A concrete base-model recommendation with justification; a data-generation strategy (with explicit synthetic-data flagging and a human-review step) prepared as scripts/prompts for the user to run; fixed input/output templates matching the chosen model's verified chat template; QLoRA (or justified LoRA) fine-tuning scripts prepared for the user to run on their own GPU environment; evaluation scripts comparing the fine-tuned model against Gemini on the defined metrics, produced only from the user's actual runs; a configurable `LocalLLMClient` integrated into Zone 2 alongside the existing Gemini/mock clients, with Gemini remaining fully functional as a fallback.

## 15. Risks and Mitigation
| Risk | Mitigation |
|---|---|
| PlantVillage/livestock class groups turn out imbalanced or an FMD class is too small to fine-tune reliably | Phase 0's dataset audit surfaces this before any training; under-supported classes are explicitly flagged and, if necessary, descoped to a documented future-scope note rather than shipped unreliable |
| Genuine MoE gate underperforms simple top-1 zero-shot heuristic | Phase 1 evaluation explicitly measures gate routing accuracy separately from expert accuracy; if the learned gate underperforms, this is reported honestly and a fallback (documented, not silently swapped) is proposed |
| Weather API unavailable/rate-limited/requires paid tier | Phase 2 selects a free-tier-compatible provider and implements graceful degradation so advisory generation never hard-fails on weather absence |
| SQLite advisory history insufficient for LLM fine-tuning (very likely per explicit requirement) | Phase 4 uses a Gemini-assisted synthetic-data strategy with mandatory human spot-check review before training, never trains on unreviewed synthetic data at scale |
| Chat template mismatch degrades fine-tuned LLM quality | Phase 4 explicitly verifies and uses the exact published template for the chosen base model before any training run |
| Cloud vector DB migration adds cost/complexity with no measurable benefit | Phase 3 requires an explicit, data-driven justification before recommending migration; default is to keep local FAISS |
| Contract drift/silent breakage across 5 phases touching Zone 1 and Zone 2 | Section 11's identify→justify→approve→modify process is mandatory for every contract touch; static cross-phase consistency checks performed at the start of each new phase's audit step |
| Fabricated/optimistic evaluation numbers presented as real | Explicit repeated rule across every phase: the coding agent reports only numbers from the user's actual executed runs; it never estimates, assumes, or extrapolates a metric it did not see the user produce |
